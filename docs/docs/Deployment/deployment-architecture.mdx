There are two broad types of Terraflow deployments:

* **Terraflow IDE (development)**: Deploy both the Terraflow visual editor (frontend) and API (backend). Typically, this is used for development environments where developers use the visual editor to create and manage flows before packaging and serving them through a production runtime deployment.

    The Terraflow repository's example [`docker-compose.yml`](https://github.com/terraflow-ai/terraflow/blob/main/docker_example/docker-compose.yml) file builds a Terraflow IDE image.

    For information about IDE deployments on Kubernetes, see [Deploy the Terraflow development environment on Kubernetes](/deployment-kubernetes-dev).


* **Terraflow runtime (production)**: Deploy the Terraflow runtime for production flows, which is headless (backend only) service focused on serving the Terraflow API. This is used for production environments where flows are executed programmatically without the need for the visual editor. The server exposes your flows as endpoints, and then runs only the processes necessary to serve each flow.

    An external PostgreSQL database is strongly recommended with this deployment type to improve scalability and reliability as compared to the default SQLite database.

    For information about runtime deployments on Kubernetes, see [Deploy the Terraflow production environment on Kubernetes](/deployment-kubernetes-prod).

    :::tip
    You can start Terraflow in headless mode with the `TERRAFLOW_BACKEND_ONLY` [environment variable](/environment-variables).
    :::

You can also [deploy the Terraflow IDE and runtime on Docker](/deployment-docker).

## Benefits of deploying Terraflow on Kubernetes

Deploying on Kubernetes offers the following advantages:

* **Scalability**: Kubernetes allows you to scale the Terraflow service to meet the demands of your workload.
* **Availability and resilience**: Kubernetes provides built-in resilience features, such as automatic failover and self-healing, to ensure that the Terraflow service is always available.
* **Security**: Kubernetes provides security features, such as role-based access control and network isolation, to protect the Terraflow service and its data.
* **Portability**: Kubernetes is a portable platform, which means that you can deploy the Terraflow service to any Kubernetes cluster, on-premises or in the cloud.

    Terraflow can be deployed on cloud platforms like AWS EKS, Google GKE, or Azure AKS. For more information, see the [Terraflow Helm charts repository](https://github.com/terraflow-ai/terraflow-helm-charts).

## Terraflow deployment

A typical Terraflow deployment includes:

* **Terraflow services**: The Terraflow API and, for IDE deployments, the visual editor.
* **Kubernetes cluster**: The Kubernetes cluster provides a platform for deploying and managing Terraflow and its supporting services.
* **Persistent storage**: Persistent storage is used to store the Terraflow service's data, such as models and training data.
* **Ingress controller**: The ingress controller provides a single entry point for traffic to the Terraflow service.
* **Load balancer**: Balances traffic across multiple Terraflow replicas.
* **Vector database**: If you are using Terraflow for RAG, you can integrate with the vector database in Astra Serverless.

## Environment isolation

It is recommended to deploy and run separate development and production environments for Terraflow:

* Deploy the IDE in your development environment where your developers prototype and test new flows.
* Deploy the runtime in your production environment to serve flows as standalone services.

![Terraflow environments](/img/terraflow-env.png)

This separation is designed to enhance security, support an organized software development pipeline, and optimize infrastructure resource allocation:

* **Isolation**: By separating the development and production environments, you can better isolate different phases of the application lifecycle. This isolation minimizes the risk of development-related issues impacting the production environments.
* **Access control**: Different security policies and access controls can be applied to each environment. Developers may require broader access in the IDE for testing and debugging, while the runtime environment can be locked down with stricter security measures.
* **Reduced attack surface**: The runtime environment is configured to include only essential components, reducing the attack surface and potential vulnerabilities.
* **Optimized resource usage and cost efficiency**: By separating the two environments, you can allocate resources more effectively. Each flow can be deployed independently, providing fine-grained resource control.
* **Scalability**: The runtime environment can be scaled independently based on application load and performance requirements, without affecting the development environment.
