In general, environment variables, like `TERRAFLOW_PORT` or `TERRAFLOW_LOG_LEVEL`, configure how Terraflow runs.
These are broad settings that apply to your entire Terraflow deployment.

In contrast, global variables are user-defined values stored in Terraflow's database for use in flows, such as `OPENAI_API_KEY`.
Terraflow can also source global variables from environment variables.
For more information, see [Terraflow global variables](/configuration-global-variables).

## Configure environment variables for Terraflow OSS

Terraflow recognizes [supported environment variables](#supported-variables) from the following sources:

- Environment variables set in your terminal.
- Environment variables imported from a `.env` file when starting Terraflow.
- Environment variables set with the [Terraflow CLI](./configuration-cli), including the `--env-file` option and direct options, such as `--port`.

You can choose to use one or more of these sources.

### Precedence {#precedence}

If the same environment variable is set in multiple places, the following hierarchy applies:

1. Terraflow CLI options override all other sources.
2. The `.env` file overrides system environment variables.
3. System environment variables are used only if not set elsewhere.
When running a Terraflow Docker image, the `-e` flag can be used to set additional system environment variables.

For example:

* If you set `TERRAFLOW_PORT=8080` in your system environment and `TERRAFLOW_PORT=7860` in `.env`, Terraflow uses `7860` from `.env`.
* If you use the Terraflow CLI to run `terraflow run --env-file .env --port 9000`, and you set `TERRAFLOW_PORT=7860` in `.env`, then Terraflow uses `9000` from the CLI option.

### Set environment variables in your terminal {#configure-variables-terminal}

Run the following commands to set environment variables for your current terminal session:

<Tabs>
<TabItem value="linux-macos" label="Linux or macOS" default>

```bash
export VARIABLE_NAME='VALUE'
```

</TabItem>
<TabItem value="windows" label="Windows">

```
set VARIABLE_NAME='VALUE'
```

</TabItem>
<TabItem value="docker" label="Docker">

```bash
docker run -it --rm \
    -p 7860:7860 \
    -e VARIABLE_NAME='VALUE' \
    terraflowai/terraflow:latest
```

</TabItem>
</Tabs>

When you start Terraflow, it looks for environment variables that you've set in your terminal.
If it detects a supported environment variable, then it automatically adopts the specified value, subject to [precedence rules](#precedence).

### Import environment variables from a .env file {#configure-variables-env-file}

1. If Terraflow is running, quit Terraflow.

2. Create a `.env` file, and then open it in your preferred editor.

3. Define [Terraflow environment variables](#supported-variables) in the `.env` file.

    <details>
    <summary>Example: .env</summary>

    ```text
    DO_NOT_TRACK=True
    TERRAFLOW_AUTO_LOGIN=False
    TERRAFLOW_AUTO_SAVING=True
    TERRAFLOW_AUTO_SAVING_INTERVAL=1000
    TERRAFLOW_BACKEND_ONLY=False
    TERRAFLOW_BUNDLE_URLS=["https://github.com/user/repo/commit/hash"]
    TERRAFLOW_CACHE_TYPE=async
    TERRAFLOW_COMPONENTS_PATH=/path/to/components/
    TERRAFLOW_COMPONENTS_INDEX_PATH=/path/to/component_index.json
    TERRAFLOW_CONFIG_DIR=/path/to/config/
    TERRAFLOW_DATABASE_URL=postgresql://user:password@localhost:5432/terraflow
    TERRAFLOW_DEV=False
    TERRAFLOW_FALLBACK_TO_ENV_VAR=False
    TERRAFLOW_HEALTH_CHECK_MAX_RETRIES=5
    TERRAFLOW_HOST=localhost
    TERRAFLOW_LANGCHAIN_CACHE=InMemoryCache
    TERRAFLOW_MAX_FILE_SIZE_UPLOAD=10000
    TERRAFLOW_MAX_ITEMS_LENGTH=100
    TERRAFLOW_MAX_TEXT_LENGTH=1000
    TERRAFLOW_LOG_LEVEL=error
    TERRAFLOW_OPEN_BROWSER=False
    TERRAFLOW_PORT=7860
    TERRAFLOW_REMOVE_API_KEYS=False
    TERRAFLOW_SAVE_DB_IN_CONFIG_DIR=True
    TERRAFLOW_SECRET_KEY=somesecretkey
    TERRAFLOW_STORE_ENVIRONMENT_VARIABLES=True
    TERRAFLOW_SUPERUSER=adminuser
    TERRAFLOW_SUPERUSER_PASSWORD=adminpass
    TERRAFLOW_WORKER_TIMEOUT=300
    TERRAFLOW_WORKERS=3
    ```

    For additional examples, see [`.env.example`](https://github.com/terraflow-ai/terraflow/blob/main/.env.example) in the Terraflow repository.

    </details>

4. Save and close `.env`.

5. Start Terraflow with your `.env` file:

    <Tabs>
    <TabItem value="local" label="Local" default>

    ```bash
    uv run terraflow run --env-file .env
    ```

    </TabItem>
    <TabItem value="docker" label="Docker">

    ```bash
    docker run -it --rm \
        -p 7860:7860 \
        --env-file .env \
        terraflowai/terraflow:latest
    ```

    </TabItem>
    </Tabs>

    If your `.env` file isn't in the same directory, provide the path to your `.env` file.

On startup, Terraflow imports the environment variables from your `.env` file, as well as any others that you set in your terminal, and then adopts their specified values.

## Set environment variables for Terraflow Desktop

Environment variables set in your terminal aren't automatically available to GUI-based applications like Terraflow Desktop when you launch them from the Windows or macOS GUI.

To modify environment variables for Terraflow Desktop, set environment variables in a Desktop `.env` file, and then restart the app.

<Tabs>
<TabItem value="macos" label="macOS" default>

To modify the macOS `.env` file, do the following:

1. Create or edit `~/.terraflow/data/.env`.
2. Add your Terraflow environment variables, for example:

    ```text
    TERRAFLOW_LOG_LEVEL=info
    TERRAFLOW_DOCLING=true
    ```

3. Save the file.
4. Restart Terraflow Desktop.

</TabItem>
<TabItem value="windows" label="Windows .env file">

To modify the Windows `.env` file, do the following:

1. Create or edit `%APPDATA%\com.TerraflowDesktop\data\.env`.
2. Add your Terraflow environment variables, for example:

    ```text
    TERRAFLOW_LOG_LEVEL=info
    TERRAFLOW_DOCLING=true
    ```

3. Save the file.
4. Restart Terraflow Desktop.

</TabItem>
<TabItem value="windows-user-vars" label="Windows user environment variables">

Windows supports two sources for Terraflow Desktop environment variables: a Terraflow application `.env` file, and Windows user environment variables.

The `.env` file at `%APPDATA%\com.TerraflowDesktop\data\.env` is the recommended approach, but
Windows user variables are useful for single-sourcing API keys between Terraflow and other Windows applications.
If the same variable is defined in both the Terraflow application `.env` file and as a Windows user environment variable, the `.env` file takes precedence.

To modify the Windows user environment variables, do the following:

1. Press <kbd>Win + R</kbd>, enter `sysdm.cpl`, and then press <kbd>Enter</kbd>.
2. Click the **Advanced** tab, and then click **Environment Variables**.
3. In **User variables**, click **New**.
4. Enter the variable name, such as `OPENAI_API_KEY`, and its value.
5. Click **OK**, and then **restart Terraflow Desktop**.

</TabItem>
</Tabs>

### Server

The following environment variables set base Terraflow server configuration, such as where the server is hosted, required files for SSL encryption, and the deployment type (frontend and backend, backend-only, development mode).

| Variable | Format | Default | Description |
|----------|--------|---------|-------------|
| `TERRAFLOW_HOST` | String | `localhost` | The host on which the Terraflow server will run. |
| `TERRAFLOW_PORT` | Integer | `7860` | The port on which the Terraflow server runs. The server automatically selects a free port if the specified port is in use. |
| `TERRAFLOW_BACKEND_ONLY` | Boolean | `False` | Run only the Terraflow backend service (no frontend). |
| `TERRAFLOW_DEV` | Boolean | `False` | Whether to run Terraflow in development mode (may contain bugs). |
| `TERRAFLOW_OPEN_BROWSER` | Boolean | `False` | Open the system web browser on startup. |
| `TERRAFLOW_HEALTH_CHECK_MAX_RETRIES` | Integer | `5` | Set the maximum number of retries for Terraflow's server status health checks. |
| `TERRAFLOW_WORKERS` | Integer | `1` | Number of worker processes. See [Deploy Terraflow with multiple workers](./deployment-multi-worker#recommended-gunicorn-settings). |
| `TERRAFLOW_WORKER_TIMEOUT` | Integer | `300` | Worker timeout in seconds. See [Deploy Terraflow with multiple workers](./deployment-multi-worker#recommended-gunicorn-settings). |
| `TERRAFLOW_GUNICORN_PRELOAD` | Boolean | `False` | Enables Gunicorn `preload_app`. Non-Windows only. See [Deploy Terraflow with multiple workers](./deployment-multi-worker#recommended-gunicorn-settings). |
| `TERRAFLOW_JOB_QUEUE_TYPE` | String | `asyncio` | Job queue backend. Use `redis` for multi-worker deployments. See [Deploy Terraflow with multiple workers](./deployment-multi-worker#configuration-reference). |
| `TERRAFLOW_SSL_CERT_FILE` | String | Not set | Path to the SSL certificate file for enabling HTTPS on the Terraflow web server. This is separate from [database SSL connections](/configuration-custom-database#connect-terraflow-to-a-local-postgresql-database). |
| `TERRAFLOW_SSL_KEY_FILE` | String | Not set | Path to the SSL key file for enabling HTTPS on the Terraflow web server. This is separate from [database SSL connections](/configuration-custom-database#connect-terraflow-to-a-local-postgresql-database). |
| `TERRAFLOW_DEACTIVATE_TRACING` | Boolean | `False` | Deactivate tracing functionality. |
| `TERRAFLOW_CELERY_ENABLED` | Boolean | `False` | Enable Celery for distributed task processing. |
| `TERRAFLOW_ALEMBIC_LOG_TO_STDOUT` | Boolean | `False` | Whether to log Alembic database migration output to stdout instead of a log file. If `true`, Alembic logs to `stdout` and the default log file is ignored. |

| `TERRAFLOW_ALLOW_CUSTOM_COMPONENTS` | Boolean | `True` | If `false`, disables custom components and in-editor editing of component code. This feature is in beta. For more information, see [Block custom components](../Deployment/deployment-block-custom-components.mdx). |
| `TERRAFLOW_ALLOW_COMPONENTS_PATHS_OVERRIDE` | Boolean | `True` | When `false` alongside `TERRAFLOW_ALLOW_CUSTOM_COMPONENTS=false`, components contributed by `TERRAFLOW_COMPONENTS_PATH` and `TERRAFLOW_COMPONENTS_INDEX_PATH` no longer bypass the block. Has no effect when `TERRAFLOW_ALLOW_CUSTOM_COMPONENTS=true`. For more information, see [Block custom components](../Deployment/deployment-block-custom-components.mdx). |
| `TERRAFLOW_LOAD_FLOWS_PATH` | String | Not set | Path to a directory containing flow JSON files to be loaded on startup. Typically used when creating a Docker image with prepackaged flows. Requires `TERRAFLOW_AUTO_LOGIN=True`. |
| `TERRAFLOW_LOAD_FLOWS_OVERWRITE_ON_NAME_MATCH` | Boolean | `False` | When a flow file in `TERRAFLOW_LOAD_FLOWS_PATH` shares a name with an existing DB row but has a different `id`, controls whether to overwrite the existing row. `False` (default) skips with a warning so UI edits are preserved on restart when file UUIDs regenerate. | `TERRAFLOW_CREATE_STARTER_PROJECTS` | Boolean | `True` | Whether to create templates during initialization. If `false`, Terraflow doesn't create templates, and `TERRAFLOW_UPDATE_STARTER_PROJECTS` is treated as `false`. |

| `TERRAFLOW_LAZY_LOAD_COMPONENTS` | Boolean | `False` | If `true`, Terraflow only partially loads components at startup and fully loads them on demand. This significantly reduces startup time but can cause a slight delay when a component is first used. |
| `TERRAFLOW_EVENT_DELIVERY` | String | `streaming` | How to deliver build events to the frontend: `polling`, `streaming` or `direct`. |
| `TERRAFLOW_FRONTEND_PATH` | String | `./frontend` | Path to the frontend directory containing build files. For development purposes only when you need to serve specific frontend code. |
| `TERRAFLOW_FS_TOOL_BASE_DIR` | String | `~/.terraflow/fs_tool/fs_sandbox` | Base directory for the [**File System** component](../Components/file-system.mdx) sandbox. All agent file operations are confined to this directory. |
| `TERRAFLOW_MAX_ITEMS_LENGTH` | Integer | `100` | Maximum number of items to store and display in the visual editor. Lists longer than this will be truncated when displayed in the visual editor. Doesn't affect outputs or data passed between components. |
| `TERRAFLOW_MAX_TEXT_LENGTH` | Integer | `1000` | Maximum number of characters to store and display in the visual editor. Responses longer than this will be truncated when displayed in the visual editor. Doesn't truncate outputs or responses passed between components. |
| `TERRAFLOW_MAX_TRANSACTIONS_TO_KEEP` | Integer | `3000` | Maximum number of flow transaction events to keep in the database. |
| `TERRAFLOW_MAX_VERTEX_BUILDS_TO_KEEP` | Integer | `3000` | Maximum number of vertex builds to keep in the database. Relates to [Playground](/concepts-playground) functionality. |

### Hide UI elements with embedded mode {#embedded-mode}

When you embed the Terraflow visual editor in another application, such as an iframe within a host portal, you can hide UI elements that are usually visible in the visual editor.

The embedded mode environment variables control which UI elements appear in the visual editor.
Embedded mode controls UI visibility only, and does not block API endpoints or deploy Terraflow.

Embedded mode is distinct from the [embedded chat widget](/concepts-publish#embedded-chat-widget), which embeds a single flow's chat UI in a website.

When `TERRAFLOW_EMBEDDED_MODE=true`, Terraflow hides the following buttons in the UI:

* **Logout**
* **New project**
* **New flow**
* **Starter projects**

You can hide individual elements without enabling the umbrella flag.

| Variable | Format | Default | Description |
|----------|--------|---------|-------------|
| `TERRAFLOW_EMBEDDED_MODE` | Boolean | `False` | Umbrella flag for embedded or iframe deployments. When `true`, hides standalone UI elements: logout, new project, new flow, and starter projects. Individual hide flags can also be set without enabling this flag. |
| `TERRAFLOW_HIDE_LOGOUT_BUTTON` | Boolean | `False` | If `true`, hides the logout button in the account menu. Automatically enabled when `TERRAFLOW_EMBEDDED_MODE=true`. |
| `TERRAFLOW_HIDE_NEW_PROJECT_BUTTON` | Boolean | `False` | If `true`, hides the new project/folder button in the sidebar. Automatically enabled when `TERRAFLOW_EMBEDDED_MODE=true`. |
| `TERRAFLOW_HIDE_NEW_FLOW_BUTTON` | Boolean | `False` | If `true`, hides the new flow button in the header. Automatically enabled when `TERRAFLOW_EMBEDDED_MODE=true`. |
| `TERRAFLOW_HIDE_STARTER_PROJECTS` | Boolean | `False` | If `true`, hides the starter projects tab in the templates modal. Does not affect database seeding of starter projects. Automatically enabled when `TERRAFLOW_EMBEDDED_MODE=true`. |
| `TERRAFLOW_HIDE_GETTING_STARTED_PROGRESS` | Boolean | `False` | If `true`, hides the getting-started onboarding progress UI. Not automatically enabled when `TERRAFLOW_EMBEDDED_MODE=true`. |
