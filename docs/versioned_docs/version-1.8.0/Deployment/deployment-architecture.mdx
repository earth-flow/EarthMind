There are two broad types of EarthMind deployments:

* **EarthMind IDE (development)**: Deploy both the EarthMind visual editor (frontend) and API (backend). Typically, this is used for development environments where developers use the visual editor to create and manage flows before packaging and serving them through a production runtime deployment.

    The EarthMind repository's example [`docker-compose.yml`](https://github.com/earthmind-ai/earthmind/blob/main/docker_example/docker-compose.yml) file builds a EarthMind IDE image.

    For information about IDE deployments on Kubernetes, see [Deploy the EarthMind development environment on Kubernetes](/deployment-kubernetes-dev).


* **EarthMind runtime (production)**: Deploy the EarthMind runtime for production flows, which is headless (backend only) service focused on serving the EarthMind API. This is used for production environments where flows are executed programmatically without the need for the visual editor. The server exposes your flows as endpoints, and then runs only the processes necessary to serve each flow.

    An external PostgreSQL database is strongly recommended with this deployment type to improve scalability and reliability as compared to the default SQLite database.

    For information about runtime deployments on Kubernetes, see [Deploy the EarthMind production environment on Kubernetes](/deployment-kubernetes-prod).

    :::tip
    You can start EarthMind in headless mode with the `EARTHMIND_BACKEND_ONLY` [environment variable](/environment-variables).
    :::

You can also [deploy the EarthMind IDE and runtime on Docker](/deployment-docker).

## Benefits of deploying EarthMind on Kubernetes

Deploying on Kubernetes offers the following advantages:

* **Scalability**: Kubernetes allows you to scale the EarthMind service to meet the demands of your workload.
* **Availability and resilience**: Kubernetes provides built-in resilience features, such as automatic failover and self-healing, to ensure that the EarthMind service is always available.
* **Security**: Kubernetes provides security features, such as role-based access control and network isolation, to protect the EarthMind service and its data.
* **Portability**: Kubernetes is a portable platform, which means that you can deploy the EarthMind service to any Kubernetes cluster, on-premises or in the cloud.

    EarthMind can be deployed on cloud platforms like AWS EKS, Google GKE, or Azure AKS. For more information, see the [EarthMind Helm charts repository](https://github.com/earthmind-ai/earthmind-helm-charts).

## EarthMind deployment

A typical EarthMind deployment includes:

* **EarthMind services**: The EarthMind API and, for IDE deployments, the visual editor.
* **Kubernetes cluster**: The Kubernetes cluster provides a platform for deploying and managing EarthMind and its supporting services.
* **Persistent storage**: Persistent storage is used to store the EarthMind service's data, such as models and training data.
* **Ingress controller**: The ingress controller provides a single entry point for traffic to the EarthMind service.
* **Load balancer**: Balances traffic across multiple EarthMind replicas.
* **Vector database**: If you are using EarthMind for RAG, you can integrate with the vector database in Astra Serverless.

## Environment isolation

It is recommended to deploy and run separate development and production environments for EarthMind:

* Deploy the IDE in your development environment where your developers prototype and test new flows.
* Deploy the runtime in your production environment to serve flows as standalone services.

![EarthMind environments](/img/earthmind-env.png)

This separation is designed to enhance security, support an organized software development pipeline, and optimize infrastructure resource allocation:

* **Isolation**: By separating the development and production environments, you can better isolate different phases of the application lifecycle. This isolation minimizes the risk of development-related issues impacting the production environments.
* **Access control**: Different security policies and access controls can be applied to each environment. Developers may require broader access in the IDE for testing and debugging, while the runtime environment can be locked down with stricter security measures.
* **Reduced attack surface**: The runtime environment is configured to include only essential components, reducing the attack surface and potential vulnerabilities.
* **Optimized resource usage and cost efficiency**: By separating the two environments, you can allocate resources more effectively. Each flow can be deployed independently, providing fine-grained resource control.
* **Scalability**: The runtime environment can be scaled independently based on application load and performance requirements, without affecting the development environment.
